# Pinned upstream KCP over Linux TAP

This benchmark carries complete Ethernet frames, including ARP and the Linux
TCP segments generated by the existing single-flow probe, between two owned
namespaces. It uses the vendored, unmodified C implementation pinned by
`simulator/src/l2tunnel_sim/_vendor/kcp/provenance.json`. Each direction sends
data and feedback on the same connected UDP socket. The initial comparison
selects raw frames. Each KCP message has a one-byte type, a two-byte length and
the entire frame. The optional independent LZ4 format uses the existing tag,
compressed length and original length and falls back to raw whenever shorter
encoding is unavailable.

## Reproduce

Choose new output directories for each build and run. The build records the
command, compiler, library versions, KCP revision, source hashes and binary
hash. It requires the C compiler, OpenSSL EVP, liblz4 and pkg-config.

```bash
python3 tools/kcp_native_reference.py build --output work/kcp-reference-build
L2TUNNEL_KCP_REFERENCE_BINARY="$PWD/work/kcp-reference-build/kcp-native-reference" \
  python3 -m unittest tools.test_kcp_native_reference
python3 tools/kcp_native_reference.py run --build-dir work/kcp-reference-build \
  --output work/kcp-reference-raw --mode raw
```

The last command prints the plan. Add `--apply` in a coordinated, privileged lab
window to create journal-owned namespaces. The runner acquires the Common native
matrix lock and copies its hash-verified binary to a mode-0700 temporary
directory on `/tmp`. It invokes the binary's argument check before creating
namespaces or keys, so the kernel's executable-mount policy is checked on the
actual private copy. The private `/run` directory holds keys and the namespace
journal. The runner removes the temporary keys, checks namespace cleanup and
preserves each receipt. The socket-pair test runs real C KCP, the cipher and both frame
endpoints in local unprivileged processes. It does not configure the network.

## Comparison boundaries

- The application is one Linux CUBIC connection with the same 4 MiB writing
  credit, two-second warmup and ten-second measured interval as the Rust TAP
  probe. Payload hash, EOF, delivery delay, kernel TCP_INFO, capture and
  per-direction qdisc evidence remain separate. The path uses the same
  100/10 Mbit/s HTB parent, 35 ms netem child and independently seeded 15%
  loss in each direction as the existing Rust TAP reference. Both native
  interfaces keep their system TX queue lengths. The runner adds no native
  pacing qdisc.
- C KCP uses one ordered, bidirectional conversation, `ikcp_wndsize(8192,8192)`
  and `ikcp_nodelay(1,10,2,1)`. This selects a 10 ms flush interval, fast resend
  threshold two and disables KCP congestion-window growth. IP MTU is 1500 bytes,
  KCP MTU is 1451 and KCP MSS is 1427. The native frame ceiling is 1514 bytes.
  C KCP fragments long messages and holds later messages behind missing ones.
  Rust Common's independently deliverable frames and feedback policy differ.
- A sender holds the full encoded KCP message against a second 4 MiB credit
  until all its C-assigned segment numbers are confirmed by a selective ACK
  or cumulative UNA that actually arrived at that sender. New PUSH sizes,
  fragment fields and sequence numbers are cross-checked against the ledger.
  Admission reserves space for a maximum-size frame before reading TAP. The
  receiver uses the standard upstream window of 8192 segments, plus space for
  one pending TAP write. Its window does not impose the Rust receiver's 4 MiB
  encoded-byte limit.
- The runner installs two fresh directional ChaCha20-Poly1305 keys locally and
  uses OpenSSL EVP for every datagram. A five-byte clear authenticated header
  carries the type and packet number. The full 16-byte tag is transmitted and
  verified before KCP input. Directional keys and monotonic counters isolate
  nonces. The replay horizon is 8192 datagrams. This benchmark starts with
  established keys and implements no Common negotiation, service management or
  interoperability with a standard KCP peer lacking this envelope.
- KCP flushes into a nonblocking connected socket. There is no extra userspace
  send queue, rate limiter or advance reservation of future capacity. KCP's own
  flush timer runs at submission. Each complete successful UDP send is charged
  for its actual C segment bytes, 21 protection bytes, 28 IPv4/UDP bytes and
  separately 14 Ethernet bytes, excluding FCS, preamble and IFG. Local socket
  refusal (`EAGAIN` or `ENOBUFS`) is counted separately from accepted datagrams.
  The socket buffer settings, largest flush, observed kernel transmit queue,
  WAN captures and qdisc snapshots expose different measurement points. A
  successful send can still be dropped downstream.
- Terminal accounting checks both ends' encoded and segment debt, pending ACKs,
  receiving queues, pending TAP writes and cross-peer native frame/byte totals.
  The post-EOF drain bound is four seconds and incomplete confirmation fails
  the arm. Byte-exact application recovery and hash validation use the existing
  TCP probe.

These options merge the paced KCP/TAP benchmark previously kept as campaign
copies under `work/kcp-tap-optimized-20261121/` (`adapter.c`, `run.py` and
their `v2/`, `long/`, `buffered/` and `rto1s/` variants). Every default
reproduces the endpoint and runner described above: the C endpoint receives no
extra argument, writes no `extensions` stats object and prints only `Ready`.
The plan JSON records every selected value, including each side's exact
endpoint arguments (`adapter_args`).

Pacing debits every accepted datagram, including ACKs and retransmissions, by
its UDP payload plus 28 IPv4/UDP bytes. Retransmission bursts can make credit
negative, so this is admission pacing, not a physical packet-rate ceiling; the
WAN shaper stays authoritative. A frame is admitted only while credit exceeds
the reservation. `queued` sums each queued segment's actual length plus 73
bytes (24 KCP header, 21-byte envelope, 28 IPv4/UDP) plus 120 bytes, which keeps
small reverse ACK frames admissible. `fixed` reserves 1500 bytes per queued
segment plus 1600 bytes, as the first campaign adapter did. The campaign's 52
bytes per segment had no authentication envelope.

Stream mode packs encoded bodies into one ordered KCP byte stream: upstream
`ikcp_send` extends the unsent tail segment to the MSS, so a full frame no longer
forces a short standalone tail datagram. The existing tag 2 and tag 10 body
headers are self-delimiting; the receiver reassembles at most one partial body
plus one segment and validates each body exactly as in message mode. The
sender ledger mirrors the tail extension and still checks each C PUSH SN,
fragment field (always 0) and size. Because a segment can carry parts of two
frames, credit retires per confirmed segment instead of per message.

The native ring drains TAP independently of KCP admission (up to 256 reads per
wakeup, up to 64 admissions per loop) so the kernel TAP queue does not drop
frames while credit, window or pacing hold admission. Ring frames are not yet
accepted. They and partial stream bodies are terminal debt
(`EXTENSION_DEBT`), so the four-second drain check also covers them.

`secure-forward16` runs one CUBIC flow with `secure_udp_native_probe.py tcp
--flows 1 --workload forward16` between the endpoint namespaces, with a common
clock 1.5 s ahead, and compares with `secure_udp_native.compare_probes(...,
flows=1)`. The single-flow-4m workload keeps `common_native_probe.py`'s fixed
2 s warmup, 10 s sample and 59 s workload, and refuses other windows. The
preset's 10 s warmup, 60 s window, 1 GiB cap and 230 s workload need the probe
limits 512 samples, 180 s deadline and 90 s maximum measurement, which the
preset passes. The workload remains inside the matrix's 300 s case bound.

Campaign mapping: the root `adapter.c`/`run.py` correspond to explicit
options without the preset: `--stream --pace-forward-mbit 95 --pace-reverse-mbit
9.5 --pace-reserve fixed --flush-interval-us 1000 --max-wait-us 100
--udp-buffer-bytes 4194304 --sample-interval-ms 1000 --udp-snmp-counters
--window 4096|8192 --workload secure-forward16 --warmup-s 5 --steady-s 20
--workload-seconds 110`; `v2/` is the same with the default queued
reservation. `long/` is the preset with `--native-queue-frames 0`; `rto1s/`
adds `--inner-rto-min-ms 1000` to that; `buffered/` is the preset itself. The
campaign's TAP link counters are part of the existing per-phase native tun0
snapshot in `qdisc_before`/`qdisc_after`. Not ported: the
campaign's unauthenticated cleartext KCP over UDP with KCP MTU 1472 (this
endpoint keeps its mandatory authenticated envelope and KCP MTU 1451), the
adapters' self-termination after 120 or 240 s and file-barrier start (the
runner stops endpoints itself), the two-byte frame length prefix (replaced by
the existing body headers), and a selectable one-way delay (the shared topology
verifies 35 ms). Their per-run results remain historical evidence of that
unauthenticated adapter, not of this endpoint.

## Optional segment trace

Add `--trace-kcp` to the `run` command to retain one CSV per endpoint.
The wrapper allocates a bounded buffer of 262,144 segment rows at each end.
Rows record KCP command, segment number, echoed timestamp, cumulative UNA,
fragment and byte counts, and the authenticated UDP packet number. For outgoing
PUSHes the wrapper observes transmission count, prior and next deadlines, and
the segment RTO. Send timestamps bracket the output callback and UDP result.
Input timestamps bracket the successful socket receive return and completion of
authenticated KCP input. The trace stores metadata only. The wrapper leaves
the pinned C engine and its timeout-before-fast-resend branch order intact.

The receipt reports `kcp_trace_analysis.status=complete` when both files validate,
no rows were dropped, every outgoing PUSH was classified, and inferred timeout
counts agree with the engine counter on every update. It then checks physical
datagrams against endpoint I/O counters. Dropped rows, unknown PUSHes or timeout
counter disagreements yield `partial_or_unclassified` and suppress the bilateral
per-segment analysis. A malformed trace fails validation. Application integrity,
terminal debt and namespace cleanup have separate outcomes. [Trace analysis implementation](kcp_native_reference.py)

The next traced raw run completed with a matching stream, zero terminal debt
and verified cleanup. The receiver counted 8,007,440 unique application bytes
during the ten-second measurement, equivalent to 6.405952 Mbit/s forward
goodput, with zero steady inner TCP retransmissions. Endpoint A retained
64,614 trace rows and B retained 63,417. First write to complete read had
P99 8,445.958 ms across

No observed timeout followed processing of a covering confirmation at the
sender. In 1,478 of the 2,417 in-flight cases, a covering datagram reached
sender WAN within 1 ms after the callback. The prior segment RTO had median
80 ms and P99 136 ms. The engine selected its timeout branch a median 3 ms and
a maximum 9 ms after its prior deadline on its update clock. On explicit ACK
input that clock trailed the monotonic processing time by a median 6 ms and
P99 10 ms. A WAN capture cannot establish when the kernel made the ACK readable
to the process. These timings identify close races and feedback loss on this
run; their effects on alternative policies require separate measurements.
